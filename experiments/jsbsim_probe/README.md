# JSBSim 연동 프로브 (계약 2 평가용)

`docs/transition_phase_contract.md` §11.5의 채택 절차 중 **2단계**(공개
순전파 모델의 C++ 연동·PVA 추출 가능성 확인)를 재현 가능한 형태로 고정한
실험이다. ROS2 빌드 그래프에 **포함되지 않는다** — 플래너는 JSBSim에
의존하지 않으며, 전환 모델 스펙이 확정되기 전에 `src/`가 이것을 링크하기
시작해서는 안 된다.

## 실행

```bash
./run.sh                      # 고정 버전 내려받아 빌드하고 둘 다 실행
./run.sh --model X15          # 다른 번들 예제 기체
./run.sh --version v1.2.1     # 다른 태그로 재검증
```

`run.sh`가 JSBSim을 `.jsbsim/`(gitignore)에 받아 빌드하고 실행한다.
재현성 규약(전부 초판 결함의 수정):

- **`$ORIGIN` 상대 RPATH** — 바인드 마운트라 상대 배치가 동일하므로,
  컨테이너(/ws)에서 빌드한 바이너리가 호스트(/home/...) 경로에서도 그대로
  돈다. `LD_LIBRARY_PATH` 불필요. (절대 RPATH였던 초판은 호스트에서 실패)
- **버전별 src/inst/build 분리** — 교차 버전 재검증이 실제 그 버전으로
  돈다. (공용 inst였던 초판은 신 lib + 구 데이터 키메라 가능)
- **고정 SHA 대조** — 태그가 움직이면 조용히 다른 코드를 재는 대신 실패.
- **소유권 감지** — root 컨테이너 셸이 만든 캐시를 다른 uid가 만나면
  명확한 안내와 함께 중단. git dubious ownership은 `safe.directory` 처리.
- **cmake 없는 호스트** — warm 캐시가 있으면 빌드 없이 재실행.

컨테이너·호스트 양쪽에서 실행 확인 완료.

## 버전 고정 근거

`v1.3.1` (현재 안정 릴리스). 처음 측정한 `v1.2.1`도 동일하게 빌드·실행되며
수치도 같은 자리에서 나온다. 굳이 옛 버전을 붙들 이유가 없어 최신으로
올렸고, `--version`으로 언제든 되돌려 확인할 수 있다.

## 이 실험이 **주장하지 않는** 것

번들 예제 기체(f16, X15 등)는 JSBSim 프로젝트가 **공개 자료로 만든 근사
모델이며 교육·오락 목적**이라고 명시한 것들이다. 따라서 여기 나오는 모든
수치는 **구조와 계산비용**에 대한 것이지, 실제 플랫폼의 비행 가능성에
대한 것이 아니다 (계약 문서 §11.3의 "물리 타당성 층"은 여전히 비어 있다).

특히 `jsbsim_probe`의 4단계 격자 탐색이 찾는 것은 **부분 인계창**
(속력 + 비행경로각) 도달일 뿐이며, **인계 성공이 아니다.** 실제 인계에는
아래가 모두 필요하고 여기서는 하나도 검사하지 않는다:

- `pvaEnvelopeProblem()` 통과
- 전역 경로 진입점과의 위치 정합 (`route_start_s`)
- 경로 접선과 속도 방향 정렬
- 가속도·하중 조건
- 인계 영역 체류
- 지형·구역 검사

## 측정 결과 (v1.3.1, f16, 12 s)

**연동·비용**

| 항목 | 값 |
|---|---|
| 빌드·링크 | ROS2 Humble 컨테이너에서 무경고, 외부 의존 libstdc++/libm/libgcc/libc |
| 라이브러리 | 3.4 MB (+ 항공기 데이터 4 MB) |
| 스텝당 비용 | 8.7~9.7 µs (12 s 궤적 = dt 0.01에서 11 ms) |
| 적분 스텝 민감도 | dt 0.001→0.02에서 12 s 후 고도차 0.3 m |
| 재현성 | 동일 프로파일 2회 비트 단위 일치 |
| 부분 인계창 격자 탐색 | 27 프로파일 × 30 s를 761 ms에, 15개 도달 |

**좌표 추출 — 고정 ECEF→ENU 프레임 (2차 수정)**

초판은 위치를 초기점 고정 평면근사로, 속도·가속도를 기체 현재 위치의
local NED(매 순간 회전)로 뽑았다 — 두 프레임의 혼용이라 삼중항이 자기
일관될 수 없었다. 수정판은 전부 **하나의 고정 프레임**이다:

```
R0     = t=0의 ECEF→NED (JSBSim 자신의 Tec2l, 1회 캡처)
p_enu  = ned2enu( R0 · (r_ecef(t) − r_ecef(0)) )      GetLocation()
v_enu  = ned2enu( R0 · v_ecef(t) )                     GetECEFVelocity()
a_enu  = ned2enu( R0 · a_ecef(t) )
a_ecef = Ti2ec·UVWidot − 2ω×v_ecef − ω×(ω×r_ecef)      (해석적)
```

가속도 후보 실측 (속도 중앙차분 기준, 피크 8.5 m/s²):

| 식 | 최대 격차 |
|---|---|
| A: 고정 프레임 해석식 (위) | 0.119 m/s² (1.4%) |
| B: `Tb2l·(UVWdot + PQR×UVW)` (이동 프레임) | 0.119 m/s² (이 짧은 호에서는 A와 동일) |
| `Tb2l·UVWdot` (수송항 없음) | 4.52 m/s² (**53.3%** — 명백히 틀림) |

A를 채택한다(원리적으로 프레임 일관, B는 긴 호에서 어긋난다). 남은 1.4%
"잔차"는 식의 오류가 아니었다 — 위치를 dt별로 추적하면 **t=1.0 s 명령
계단의 액추에이터 응답 구간에 정확히 고정**되고, 그 구간을 빼면 잔차도
dt와 함께 수렴한다(0.036 → 0.0015 m/s²). 즉 물리적 불연속이지 프레임
오차가 아니다.

**소스 자기 일관성 (수정 후)**

| 검사 | 결과 |
|---|---|
| \|d(p)/dt − v\| | 0.019 m/s (속력의 0.010%), **dt와 함께 O(dt²) 수렴** (0.0035→0.000065) |
| \|d(v)/dt − a\| (명령 계단 응답 [0.95, 1.40 s] 제외) | **dt와 함께 수렴** (0.036→0.0015 m/s²) |
| 〃 (전 구간) | 0.12 m/s², 비수렴 — 위치가 t=1.0⁺에 고정 = 계단 응답의 실제 불연속 |

**PVA → 5차 Hermite 재표현 (프레임 수정 후 — 유효한 측정)**

| knot 간격 | 조각 | 내부 dP | 내부 dV | 내부 dA |
|---|---|---|---|---|
| 0.10 s | 120 | 0.4 mm | 0.002 m/s | 0.13 m/s² |
| 0.50 s | 24 | 2 mm | 0.016 m/s | 0.50 m/s² |
| 2.00 s | 6 | 0.40 m | 0.74 m/s | 4.75 m/s² |

- knot P/V/A 일치 1e-14, 접합 C⁰/C¹/C² ≤ 1e-13 — 구성상 정확.
- **P/V/A 내부 오차가 knot 세분화와 함께 전부 수렴한다** — 초판에서
  "속도 오차 1.03 m/s 고정, 가속도 오차는 촘촘할수록 악화"로 보였던 것은
  전부 프레임 혼용의 산물이었고, 다항식 고유 성질이 아니었다.
- jerk: 피크 35.1 m/s³, 접합 점프 34.6 m/s³ (초판 529는 프레임 오차의
  증폭) — 명령 계단이 있는 곳에 국한된 실제 jerk다. 상한 판정은 §8 스펙
  대기.
- 출력 PVA의 p는 초기점 기준 변위다 (프레임이 t=0에 고정되므로).

⇒ 완료의 정확한 범위: **JSBSim 예제 모델에서 고정 ENU PVA를 조각별 5차
다항식으로 재표현하고 C² 연결할 수 있으며, 근사 오차가 knot 간격에 따라
수렴함을 확인했다** — 표현 계층 검증까지. 실제 전환 인계·실행 가능성·
적절한 knot 간격·jerk 상한은 완료가 아니다(§8 스펙 대기).
