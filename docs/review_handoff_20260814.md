# 초기 전환 플래너 실기 검증 — 인수인계 (2026-08-14)

`lgh/initial-planner` 브랜치의 라이브 스모크 결과와, 그 과정에서 드러난 계측 결함
두 건을 적는다. 순서는 **틀린 것 먼저**다.

---

## 1. 판정

초기 전환 플래너는 실기 검증을 통과했다. 앞선 라운드에서 관측한 전면 실패는
플래너 회귀가 아니라 **잘못된 시나리오 조합**이었다.

| 조합 | 결과 |
|---|---|
| `r5_transition_success_probe` + 구역 0 | CLEAN, 343조각, 1114.7 s, `enumerated 10, winner 9` |
| `r5_transition_reject_probe` + 구역 0 | REJECTED — "commanded start acceleration is not flyable by the model", `enumerated 0` |
| `r5_extended_corridor` + `r5_corridor_wall` | CLEAN, 281조각, 1143.7 s |

`enumerated 10, winner 9`와 1114.7 s / 343조각은
`path_manager_20260811_044828.log` 및 `transition_v1_impl_notes.md`의 기록과
정확히 일치한다. 생성기와 물리 임계값은 이번 라운드에서 **변경하지 않았다**.

증거: `/tmp/sm8.log`(성공), `/tmp/sm6.log`(오조합 실패), `logs/runtime/replan_fsm_drone_0_20260814_092430.log`(감사 계수).

## 2. 기제 설명 — 좁혀야 하는 주장

커밋 `687d493`의 메시지는 "구역이 회랑 크롭을, 따라서 경로를, 따라서 전환 기하를
바꾼다"고 적었다. **이 인과 사슬은 측정되지 않았다.** 커밋 메시지는 고칠 수 없으므로
정정을 여기 남긴다. 정확한 서술은 다음과 같다.

> 잘못된 시나리오 조합이 전역 경로와 전환 후보 기하를 바꿨으며, 전환 구역 접촉
> 게이트가 직접 탈락시킨 후보는 없었다. 크롭과 위험 비용의 개별 기여는 분리
> 측정하지 않았다.

감사 계수로 확정된 것은 딱 여기까지다:

```
enumerated 24, winner -1, zones 8
disq  fin 0  pre 0  rep 0  sat 4  ter 6  zone 0  zone_standoff 0
      limits 0  time 14  pva 0  adapter 0        (4+6+14 = 24 = enumerated)
```

`zone`·`zone_standoff`가 모두 0이므로 **구역 접촉 게이트는 후보를 하나도 떨어뜨리지
않았다**. 해당 시나리오는 회랑 크롭뿐 아니라 위험 비용을 통해 FM2 경로도 바꿀 수
있으므로, 두 기여를 가르려면 별도 A/B가 필요하다. 하지 않았다.

부수 정정: 앞선 보고에서 `r5_corridor_wall`의 구역을 40개로 읽었다. `risk_zones`는
5필드 평탄 배열이므로 **8구역**이 맞다.

## 3. 계측 결함 두 건 — 둘 다 이쪽 것

### 3-1. 실패 사유가 콘솔에 나오지 않았다 (`687d493`)

`PlanResult.reason`/`.detail`이 `FSM_LOG_ERROR`로만 나갔다. `enable_debug_logs`에서
FSM 매크로는 파일 로거로 가고, 헤드리스 실행은 `disable_file_logging`을 켠다. 결과로
미션이 거부된 **이유가 어디에도 남지 않고** 일반 문구
`Unable to generate global trajectory`만 보였다. 원인 추적에 라운드 하나를 썼다.

이제 `RCLCPP_ERROR`가 무조건 출력한다. 파일 로거는 추가 기록만 한다.

같은 커밋에서 `[S13] transition audit`이 `disq_zone_standoff`를 누락하고 있던 것도
고쳤다. 1.05x 라우팅 셸만으로 후보가 전멸한 경우와 authored volume 내부에서 전멸한
경우가 구분되지 않았다 — 그 구분이 바로 standoff 계수의 존재 이유다. 구역 수도 함께
찍는다. 오조합은 생성기 회귀와 똑같이 보이기 때문이다.

### 3-2. 하니스가 기다리던 궤적을 스스로 먹고 있었다 (`279bf0d`)

영수증 게이트가 궤적 콜백의 딕셔너리와 **같은 이름 `got`을 재사용**했다. 게이트가
지나간 뒤 `got`은 float 5개짜리 리스트였고, 이후 모든 `/planning/trajectory` 메시지가
콜백 안에서 `AttributeError`로 죽었으며 `'traj' not in got`은 영구히 참이었다.

> 이 게이트가 들어간 뒤 하니스가 출력한 `FAIL: no /planning/trajectory`는
> **플래너에 대한 증거가 아니다.** 플래너가 직접 찍은 `[PLAN] FAILED`는 독립적이라
> 유효하다.

같이 고친 것:
- 영수증 대조가 상대 허용오차였다. 원점 ~3658 u에서 1e-3 상대는 3.7 u를 통과시킨다 —
  확인하려던 0.4 u 해상도의 9배다. 절대 허용오차로 바꿨다:
  원점 `max(resolution, 0.01)`, extent 그 2배
- 실행이 자기 입력 파일명을 찍지 않았다. 장애물 시나리오는 헤더가 지목한 미션에
  속하며, 다른 미션에 붙이면 플래너 회귀처럼 읽힌다. 이제 둘 다 출력한다

## 4. `[FM2-FINAL-CLEAR]` 최종 게이트 회귀 — 절반만 걸려 있었다

변이로 확인한 결과는 갈렸다.

| 변이 | `dynprobe` 결과 |
|---|---|
| 최종 게이트 전체 삭제 | **FAIL 3** — `[TAKEOFF]` chain/handoff/derived가 전부 계획 성공으로 뒤집힘 |
| `polylineClear`의 **장애물 절반**만 삭제 | **PASS** — 68 variant 전체가 깨끗하게 통과 |

즉 지형 절반은 이미 `dynprobe`가 고정하고 있었고(그 사실이 문서에 없었다), 장애물
절반은 **회귀가 전혀 없었다**.

장애물 절반에 픽스처를 만들 수 없는 이유가 있다. 하니스가 만들 수 있는 장애물은
`groundedCenter`로 전부 지면에 붙는다. 지형 리프트는 z를 올리므로 지면 부착 장애물
**바깥으로만** 움직인다 — 리프트가 장애물 안으로 들어가는 경우가 구성되지 않는다.
장애물을 더 넣어서 해결되는 문제가 아니다.

그래서 **순수 술어로 진술했다**: 새 variant `finalclear`.

- `polylineClear`/`polylineObstacleClear`/`terrainClearanceShort`/`obstacleBlocked`/
  `startTerrainReliefArc`를 public으로 옮겼다. 전부 질의이고 상태를 바꾸지 않는다
- 픽스처는 두께 0의 슬래브와 폭 2 u 능선. 슬래브 두께가 0인 것은 의도다 —
  폭을 주는 것은 `obstacle_margin_`이므로 마진의 역할이 기하 안에 숨지 않는다
- 고정하는 것: raw/final 분리, 지형 완화의 **arc 예산**, 장애물 무예외,
  arc가 반경이 아니라 **경로를 따라** 측정된다는 것, arc가 정점마다 리셋되지 않는다는 것,
  구간 **내부**를 표본한다는 것, 퇴화 입력의 fail-closed

변이 6종 전부 죽는다 `[재현: finalclear]`:

| 변이 | 죽은 검사 수 |
|---|---|
| 장애물 절반 삭제 | 2 |
| 지형 절반 삭제 | 6 |
| arc → 시작점으로부터의 반경 | 1 |
| arc가 구간마다 리셋 | 1 |
| raw 단계도 지형을 검사 | 1 |
| 정점만 검사(내부 표본 없음) | 7 |

## 5. 남는 것

- **RC 태그 이후에도 main 머지는 별도 승인 사항이다**
- `[FM2-FINAL-CLEAR]` 장애물 절반은 순수 술어로만 고정돼 있다. 프로덕션 경로에서
  이 절반이 실제로 발화하는 경우는 아직 없다 — 지면 부착 장애물만 존재하는 한
  방어적 가드다. 부착되지 않는 장애물이 생기면 통합 픽스처를 다시 봐야 한다
- 크롭 기여와 위험 비용 기여의 분리 측정(§2)
- 성공 계획 뒤 같은 노드에 미션을 재전송하면 FSM이 `SEQUENTIAL_START`에서 무시한다.
  **플래너를 바꾸지 않는다** — 활성 궤적 실행 중 새 명령을 무시하는 동작은 옳고,
  시험 편의로 바꿀 것이 아니다. 하니스가 시나리오마다 새 스택을 띄운다
- 빌드는 컨테이너 안에서만, `docker exec -u 1000:1000`
- 모델 기반 결과는 전부 "프로젝트 정의 중립 3DOF 벤치마크 기반 구조 검증이며 실제
  플랫폼 물리 검증이 아니다"
