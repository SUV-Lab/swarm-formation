### 0.1 환경 setter 직호출과 채택된 비행의 재검증 — 계약 문제, 문서 우선순위 high (confirmed)

- 주장: mission_planner.h:12-13 "Live environment updates during execution retain the ROS adapter's existing revalidation and trajectory withdrawal policy", planning_library_usage_ko.md:170 "갱신은 기존 실행 계층의 재검증·궤적 철회 정책을 따른다".

- 권고(코드 변경 없음): 두 문장을 "파사드 setter는 계획 환경만 갱신한다. 채택된 비행의 재검증·철회는 ROS 런타임(ReplanFSM 토픽 콜백)에만 있으며 파사드 setter는 수행하지 않는다(예외: 새 지형으로 SDF가 준비될 때의 지연 장애물 flush)"로 정정. 파사드에 재검증 진입점을 둘지는 별도 설계 결정(범위 밖, 재확인 표시).

## 1. A_facade_request_result

**요약(검토자 원문):** Area A (whole-mission facade, request/result, backend contract, settings vs environment vs request, start-state provenance, status vocabulary). Verdict: the facade's names are mostly right and a mass rename isn't justified. MissionPlanner, MissionPlanRequest, MissionPlanResult, MissionPlanningBackend, PlanSettings.attach_visualization, StartHead, StartStateSource, the *_u unit suffixes and the CMake targets all describe what the code does. What causes real misreadings is mostly contracts the header doesn't state, not the names themselves:
(1) Some MissionPlanRequest fields act as planner-level persistent state, not per-request input. length_per_piece and obstacle_clearance persist, and a later 0 cannot reset them. formation_pattern and formation_size reach the optimizer only AFTER a successful solve, so they affect the next solve, not this one. formation_type is stored and never read (ros_planning_backend.cpp:314-328, path_manager.cpp:1753-1759).
(2) MissionPlanner::plan() adopts the result into the ROS backend's execution store. That consumes trajectory IDs and can invalidate the active slot. The facade header does not say so.
(3) TerrainGrid does not state the index direction. Row 0 sits at max X and col 0 at max Y (terrain_data.h:14-15, 44-47), so a natural raster fill silently mirrors the terrain.
(4) Obstacle and risk-zone z may be ignored or re-grounded depending on configuration.
(5) The status vocabulary is split. The struct named PlanResult holds only status, while sibling APIs use *Status enums. FlightVerdict.evaluated=false has two meanings. The PlanReason comments are stale ("last two are FAILED-only", but there are now 9 FAILED-only reasons, and the priority order comes from enum order).
(6) Two comments contradict the code: the -1/-2 obstacle return codes (path_manager.h:402 vs mission_planning_backend.h:24-25).
Narrow renames worth considering, all with few callers: DirectPlanSettings (it is not used by the chain-disabled 'direct' path; it is the chain's per-call direct-solve overlay), RosPlanningBackend::setTerrainData (it takes a GridMap, not TerrainData, and discards the acceptance result; 0 non-test callers), parseStartClaim's unit_m parameter (renaming a parameter has no caller cost), mayClamp to mayFloor, and PlanSetting to PlanSettingValue. Optional, with an alias to keep source compatibility: PlanResult to PlanStatus and PlanningEnvironment to PlanningEnvironmentPatch. No actual behaviour bug was confirmed in this area. One diagnostic-message issue needs re-verification (the 'became stale' text can mask an internal structural rejection). Reference counts exclude reports/, experiments/, docs/ (docs/validation holds frozen source copies), build/, install/ and log/. Tests are counted separately.

## 2. B1_calculations_core

**요약(검토자 원문):** B1 (reusable calculation core: route search/profile, slice/batch, direct solve, assembly, evaluation, sampling helpers) — read-only audit. Overall verdict: KEEP the function names. They are already verb-first and fairly accurate (searchMissionRoute, prepareRouteProfile, solveRouteSlice, solveRouteSliceBatch, solveDirectTrajectory, stitchRouteFlight, evaluateFlight, formatFlightEvaluation). The header comments on ownership, borrowing and synchronous behaviour are unusually thorough, and they match the implementations I checked (route_slice_batch.cpp joins on unwind, solveDirectTrajectory keeps optimizer_path/piece_leg on failure, the evaluator returns before any callback on malformed input). Renaming is not where the value is. The real problems are:
(a) A small number of names that say something false about what they hold. The biggest is the FlightPhaseMetrics::zone_hard_{t_first,t_last,runs,qmin*} group, which also records contact with the standoff shell, not just hard contact. Next are the public member SegmentChainPlanner::evaluateFlight, which has side effects and shares its name with the pure free function evaluateFlight, and DirectAltitudeBand::path_max_z.
(b) Contracts that rely on hidden sentinel values or units not stated in the headers: the FlightVerdict::clean default of true, ground_height <= -0.5 meaning 'no floor', the elevation invalid encoding (<= -1e9 / NaN / -inf), the mixed-unit junction_pva_tol_u, v_floor in curvature3 meaning m/s, and obstacle_clearance in the evaluator meaning only an AGL band that does not affect the verdict.
(c) A boundary gap. Every header in include/ is installed (CMakeLists.txt:782). The consumer README (examples/library_consumer/README.md:34) advertises 'geometry/route/assembly helpers' as entry points of path_manager_calculations, yet the public-header table in modularized_function_api_ko.md:59-79 lists none of the B1 calculation headers. Their supported or internal status is therefore undefined.
(d) Inconsistent vocabulary: slice vs segment vs 'seg' vs piece vs edge, cap vs cap_ref, envelope_peak vs util_peak, and three terrain-query shapes. This needs a glossary, not a mass rename.
There are no external-package callers. The B1 headers are included only from path_manager src/include/test (grep across the src tree, excluding docs/reports/experiments). So the narrow renames proposed below cost only in-repo edits plus doc/figure text, apart from the unknown risk to installed-header consumers.
I suspect two behaviours, both marked for re-verification and kept separate from naming: (1) the formatFlightEvaluation CHECK line omits the cause for a failure on envelope peak alone; (2) the baseline-chain span labelling duplicates stitchRouteFlight. Neither changes a verdict.

## 3. B2_geometry_risk_phases

**요약(검토자 원문):** B2_geometry_risk_phases (path_manager): read-only naming and boundary audit of mission_geometry.h, terrain_risk.h, zone_policy.h, risk_zone.h, terminal_phase.h, transition_phase.h, waypoint_eval.h and terrain_data.h. I read them against their .cpp files, their main callers (path_manager.cpp, segment_chain_planner.cpp, flight_evaluator.h/.cpp, planning_environment_store.cpp), the CMake install/export setup and docs/design/modularized_function_api_ko.md.

Overall verdict: no mass rename is needed. Most names in this area say what they do, and many already carry units in the name (_m, _mps, _s, u). The real problems fall into four groups.

(1) One name that actively misleads about units: `EntryCandidate::route_start_s` and `TransitionResult::route_start_s`. The `_s` suffix means seconds on every other field in transition_phase.h, but this value is an arc length in planner units.

(2) The terrain callbacks. Four of them share one shape, `std::function<bool(double,double,double*)>`, under three names, and the units differ:
- `TerminalPhase::helixDescent(..., terrain_z)` takes planner units.
- `TransitionRequest::terrain_z` and `waypoint_eval::SafetyHooks::terrain_z` take metres.
- `FlightEvaluationEnvironment::terrain_elevation` has a different rule for what happens on a false return.
- `ElevationQuery` in mission_geometry is a fifth form: it returns a float sentinel instead of a bool.

(3) Contract issues where the name is fine but the stated contract is not:
- `ZonePolicySnapshot::valid` defaults to true (fail-open). flight_evaluator.h:65-67 has to force it to false. A test, flight_evaluator_test.cpp:70, relies on the true default.
- The two `TerrainData` accessors disagree about all-water cells: `getElevation` returns -inf, while `getElevationAndGrad` returns true with h=0. This is documented only inside the function bodies, not at the declarations.
- `synthesizeCommands` hides a 1.02/0.98 shrink of the speed window, and waypoint_eval.cpp has to back-solve it.
- The meaning of `valid` differs between a plan-wide snapshot and a per-leg snapshot.
- Units (planner u vs m) and invalid-elevation sentinels are not stated in mission_geometry.h or terrain_data.h. risk_zone.h hard-codes "1 unit = 100 m", while the chain reads a configurable `dynamics_unit_xy_m`.

(4) The public/internal boundary is blurry. Every header under include/ is installed (CMakeLists.txt:782). The documented public-header table (modularized_function_api_ko.md:59-70) lists only terrain_data.h and terrain_risk.h from this area. mission_geometry.h, zone_policy.h, terminal_phase.h, transition_phase.h and waypoint_eval.h are compiled into `path_manager_calculations` and installed, but their status is not stated. waypoint_eval has no production caller, only the two experiment tests. transition_phase.h exposes harness-only internals: `rk4Step`, `synthesizeCommands`, `wrapPi`, `invertPointMassCommands`, `pointMassAcceleration`.

Two behaviours look wrong and are reported separately as suspected bugs that need re-checking:
- `validateTransitionTrajectory` calls `req.zone_probe` without a null check, so a missing probe throws `std::bad_function_call`. It also silently skips the AGL gate when `terrain_z` is null, a case `generate()` refuses.
- `terminal_phase.cpp:79` calls `terrain_z` unconditionally.

Suggested priority:
- High: narrow rename of `route_start_s` (10 code references); fix the `ZonePolicySnapshot::valid` default, or at least document it.
- Medium: units for the `terrain_z` callbacks; the `TerrainData` water contract; a boundary table for the installed-but-unlisted headers; the `synthesizeCommands` contract.
- Low: everything else.

## 4. C_optimizer_api

**요약(검토자 원문):** Area C_optimizer_api (path_optimizer package, namespace ego_planner). The new solve boundary is well named: OptimizerSolveRequest/OptimizerSolveResult/OptimizerSolveStatus, setRuntimeSettings/setEnvironment/setRiskEnvironment, seed/trajectory, edge_leg/piece_leg, TailBoundary prescribe_vel/prescribe_acc and buildPieceAltitudeCaps/buildPieceRoughness. Most of them should be kept. A rename is clearly worth it in only two places: (1) OptimizerSolveRequest::max_vel, which is really the seed and arrival cruise speed, while the same class has a separate optimization/max_vel limit; (2) the generic LOG_INFO/LOG_WARN/LOG_ERROR macros that leak from the installed poly_traj_optimizer.h into every path_manager consumer. Both are cheap now: 2 production callers for max_vel, and 0 external users of the macros. A free parameter-name fix (out_global/out_local to out_seed/out_trajectory) is also worth doing. The main problems are contract and documentation problems, not names. (a) Only waypoints.back() is used, as the tail position; all waypoints serve only as risk-barrier/taper anchors; path.front()/back() are replaced by head_pos and waypoints.back(). None of this is said in the request header. (b) Sentinel values are undocumented: ground_height/virtual_ceil_height <= -0.5 disables, and the default of -1 silently disables the crash-plane barrier for standalone users. Band z_hi < 0 means no cap. (c) The optimization/* yaml namespace is split. setParam ignores the lbfgs_*, collision_reject, audit_envelope_* and obstacle_clearance keys, which path_manager reads into OptimizerRuntimeSettings. (d) route_cost_profile claims to work in any consistent units, but it hard-codes constants on a 1 u = 100 m scale. (e) OPTIMIZER_FAILED also covers audit rejection, and the result comment says provenance survives refusal while piece_leg is always empty on failure. (f) optimizeFromPath is called the 'single replaceable seam', but it is non-virtual and superseded by solve(). (g) Legacy individual setters have no production callers outside the optimizer's own delegation, and they are not marked as compatibility API. The boundary also leaks internals: lbfgs.hpp, root_finder.hpp, FORMATION_TYPE, ConstrainPoints, the public OptimizeTrajectory_lbfgs, the public prepareRiskBarrier/markFrontEndCrossings, and a shared log_manager.hpp installed to <prefix>/common by three packages. **요약(검토자 원문):** Area D (replaceable interfaces): VehicleModel (mmp_vehicle_dynamics), RouteSearchBackend with BuiltinRouteSearchBackend and the ROS config reader (path_manager), and the path_planner types reachable through them (PathSearcher, IDistanceField/SDFManager, risk_shape, FM2 GPU/eikonal headers, CMake exports). ## 6. E_environment_execution_ros

**요약(검토자 원문):** Area E (environment/execution stores, ROS backend + adapters, remaining PathManager/SegmentChainPlanner/ReplanFSM public surface, CMake target split). Overall verdict: KEEP almost all names. The split is sound. PlanningEnvironmentStore owns the live world. PlanningExecutionStore owns the slot, IDs and revocation. PathManager is the adapter that coordinates them. RosPlanningBackend is the explicit ROS compatibility backend. The compute (no adoption) vs plan (compute + apply) verb convention holds for PathManager, SegmentChainPlanner and RosPlanningBackend; the only exception is planCommittedRoute, which plans a route and never adopts. The real problems are contract and documentation gaps, not naming taste: (1) ExecutionReceipt.applied is true for accepted no-product failures and then reports the slot's PREVIOUS trajectory_id. (2) The compute* entry points are not side-effect free: they persist overrides, set formation on the optimizer, publish viz, and through prepareRoute->flushPendingObstacles can revoke the active flight and emit an ABORT. (3) Several header comments are stale: PathManager add* return codes, the SegmentChainPlanner::compute doc block, and the ReplanFSM callback-group/threading doc. (4) Users of the new compute API must reach the legacy PathManager through RosPlanningBackend::executionManager() to apply a result, so the new/legacy boundary leaks. (5) "Global" means three different things (the whole-mission direct solve, the reference/seed slot, and /planning/initial_trajectory). Narrow renames are justified only where caller counts are tiny and the name actively misleads: ExecutionRevocation::detected_time (trajectory-relative, wire name detected_trajectory_time), invalidateStoredTrajectoryForEnvChange (hard-codes POLICY_UNEVALUATED, 1 caller), PathManager::dynamicsParams (same name as the optimizer's, different contract), and optionally setTransitionActive, SegmentChainPlanner::segments() and deliverTrajToOptimizer. A rename of computeGlobalTrajectory or planGlobalTraj is not worth the cost now; document instead. Thread/serialization expectations are stated per method in most headers, but there is no class-level statement on PathManager, and the one explicit threading comment in replan_fsm.h is wrong. One suspected behaviour issue needs re-verification: the abort's detected trajectory time is the check start t0, not the time of the blocked point. Caller counts exclude reports/, experiments/, docs/ and the docs/validation snapshot copies; test references are counted separately.

## 7. F1_simulation_terrain

**요약(검토자 원문):** F1 (simulation engine + ROS-independent Python map loading) is in reasonably good naming shape. Most public names show units (_m, _mps, _s, _u), ownership (takeResult() &&, owned SimulationInput/SimulationResult, a newly allocated elevation_u) and side effects (resolve_map_mission/load_map docstrings say what they read). I do not recommend a broad rename. Findings fall into four groups:

(1) Frame/axis contract (highest value): point_mass_eom.hpp:12 calls the frame "mission ENU", but [TERRAIN-FRAME] (frame.py:59-64) is +x NORTH, +y WEST, z up. So heading_rad is measured from north toward west, not compass and not ENU yaw. elevation_u[0,0] is the max-x/max-y (north-west) corner, not min_bound_u. These need doc fixes, not renames.

(2) Two narrow, low-cost rename candidates in the C++ simulation API: SimulationSession::controller(t,state), which returns a realized control yet shares its name with the SimulationInput::controller strategy field (1 test caller), and SimulationMetrics::violation_steps, which is really an envelope-violation count; path_manager already uses env_violation_steps (1 node and 3 test references).

(3) Python map API vocabulary: the word "mission" names three shapes (mission.Mission, ResolvedMapMission exposed as MapLoadResult.mission, and the ResolvedMission ROS msg), which forces result.mission.mission. normalize_elevation returns a MapLoadResult, masks <=0 m to NaN and takes a unitless actual_cell_size. vrt_resolution/full_map_override hide unit/type/None-vs-'' semantics. Document first; renames only with aliases.

(4) Doc drift: the mmp_vehicle_dynamics/__init__.py docstring cites a stale config value and a non-existent mmp_dynamics_sim package. A comment on SimulationReference belongs to PolynomialReference. load_anchor is a compat wrapper with 0 callers whose docstring names a caller that does not use it.

One suspected (minor) bug: parameters_from_ros uses `or 100.0`, which silently replaces 0 for the frame units. It needs re-verification.

Boundary: all 5 vehicle_dynamics headers are installed via install(DIRECTORY include/). trajectory_abort_state.hpp is an execution-protocol helper that lives in the dynamics package, and path_manager's test uses it. mmp_terrain/__init__.py is empty, so public vs ROS-bound modules are separated only by module name (ros_terrain, terrain_publisher). The Python simulation API is intentionally not bound (README:180).

**용어 불일치:**
- Frame axes: point_mass_eom.hpp:12 says 'mission ENU'. frame.py:59-64 and terrain_data.h:13-14 define [TERRAIN-FRAME] as +x north, +y west (mirrored grid). mission.py:9 says 'wx tracks northing, wy tracks easting'. 'ENU' appears nowhere else in vehicle_dynamics/path_manager headers, so the EOM comment is the outlier.
- Frame unit (100 m) has three names: TARGET_CELL_SIZE_M (frame.py:86; 21 refs in 6 files), FrameUnits.xy_m/z_m (mmp_vehicle_dynamics/__init__.py:43-46), and PolynomialReference::unit_xy_m/unit_z_m (trajectory_simulation.hpp:24). ### 9.4 Codex 초안과 다른 판단

1. README 2.2가 FlightVerdict를 "evaluated=false 의미 설명"(문서)으로만 두는 것은 약하다. 내 검증자 둘(B1·F2)이 독립적으로 high/medium contract로 확정했고 planner 자체 코드가 두 번 걸린 흔적이 있다. 최소한 tri-state 헬퍼 추가를 "계약 확장 후보"(README 6절)에 올려 달라.
2. README에 ground/ceil 센티널과 −0.1 기본값(N3·N4)이 전혀 없다. 외부 라이브러리 사용자를 위한 조사라는 취지에서 이것이 가장 실질적인 함정이다(YAML 없이 쓰면 경로 없음).
3. TerrainGrid 방향·단위(N1)도 README에 없다. 새 C++ 값 입력 사용자가 가장 먼저 만나는 구조체다.
4. README 3절의 좁은 개명 후보에 N7(zone_hard_* → zone_contact_*), N8(invalidateStoredTrajectoryForEnvChange), N9(SimulationSession::controller)를 추가 제안. 셋 다 호출자가 2파일 이하이고 외부 소비자가 없다.
5. 나머지는 판단 차이가 아니라 누락이며, 모두 문서 보강으로 흡수 가능하다.
