## 2. 변경 목록 (커밋 순)

### 2.1 `47e889c` FM2 속도맵 열 호이스트 — 비트 동일 최적화

`fm2BuildSpeedMap`이 셀마다 `terrain_height_`·`terrain_hgrad_`
(`std::function` 간접 호출)를 불렀다. 둘 다 (x,y)만의 함수인데 z축이
109셀이라 36.4M회 호출, 실제 필요한 열은 334k개.

열을 미리 풀어 재사용. 쓰기 순서는 유지(`fm2Flat = i + fcnx_*(j+fcny_*k)`
라 k를 안쪽으로 돌리면 한 걸음에 1.3 MB를 건너뛴다).

- 주장: **비트 동일**. 근거 — 실미션 재계획이 343조각·1114.8 s·구간별
  조각 수(2/45/39/38/39/84/27/2)·`wp=3618`까지 일치
- 효과: eikonal 372.0 → 320.6 ms
- **검토 포인트**: `getRoughCost`를 `getRoughCostCol`에 위임하도록
  리팩터했다. 원본은 `agl >= kRoughAglFar`일 때 hypot 계산 전에 반환했는데
  새 경로는 항상 계산한다. 값은 같다고 봤지만 확인 바람
  (`dyn_a_star.h` `roughColumn`/`getRoughCostCol`)

### 2.2 `2410bdb` 접합 선정 결함 — 이번 작업의 근본 원인

`authorContractsFromRoute`의 자유 접합 탐색:

```cpp
for (int i = 1; best < 0 && i + 1 < M; ++i)   // 결함
for (int i = 1; forced < 0 && i + 1 < M; ++i) // 수정
```

`best < 0`이 루프 조건에 있어 **첫 적격 정점에서 멈췄다**. 바로 아래
"곡률 우선, 균형이 동점을 가른다" 채점 블록이 한 번도 실행되지 않았다.
모든 자유 접합이 창 하단에 붙어 한 구간이 경로의 78%를 떠안았다.

증거: 창 하단 33.6+0.2×1052.4 = 244.1, 선택된 접합 253.1, 균형 목표 1085.
solves `[1/8/1017/1] ms`.

`forced`를 쓰는 이유: `best`면 첫 후보에서 멈추고, 조건을 아예 지우면
강제 접합(단계 인계)을 덮어쓴다.

같이 바꾼 기본값:
- `chain/difficulty_balance: true` (호장이 아니라 난이도로 균형)
- `chain/auto_pieces_per_segment: 70 → 35`
- `enable_lbfgs_detail_logs: true → false`

**검토 포인트**: `difficulty_balance`는 원래 "r4에서 구간 기각
28.7%>25%"라는 이유로 꺼져 있었다. 그게 이 결함이 있던 상태의 결과라고
판단해 켰다. 재측정에서 기각·재시도 0건이었지만, 그 판단 자체를 봐 달라.

### 2.3 `93849d2` + 상위 `e6ae8db`/`99ff50e` 전이 런치 스위치

`mmp.launch.py`는 플래너를 띄우지 않는다. RViz "MMP Control" 패널이

전달. 3상태(빈 값=yaml 권위, 1=강제 on, 0=강제 off).

### 2.4 `37fc51a` `transition/enable` 기본 true

사용자 범위 정정("무조건 초기+중기+말기 다함")에 따름.

측정된 영향:
- 플래그 때문에만 거절되던 미션이 계획됨
- 가파른 시작을 요구 안 한 미션은 무영향(r4 전이 구간 0줄)

  아니라 생성기가 후보를 다 따진 뒤로 밀린다.** 이건 계약 변경이다.

`initfail`/`initaccfail`/`initceiling`/`pvaprobe` 4개 변형이 플래그를

바뀐 동작을 단언으로 바꿨어야 하는지.

### 2.5 `45fedd7` + 상위 `7ab487f` 초기 상태를 지어내지 않음

미션이 초기 속도를 안 적으면 정지 상태 → 실속 바닥 미달 → `[STALL-FLOOR]`
(및 체인 모드 쌍둥이)가 **131.8 m/s로 재작성**했다. 경고문은
"commanded start speed 0.000"이라 적는데 지시된 적 없는 값이다.
**출하 미션 10개 중 8개**가 이 상태였다.

두 구멍, 한 원칙(선언된 건 안 고치고, 없는 건 안 채운다):
- 없음 → 새 사유 `INITIAL_STATE_UNSPECIFIED`로 계획 전 거절.
  `start_state_stated_`가 출처를 나른다(지시 벡터 / `initial_speed` /
  테스트 주입 / 궤적 유래 재계획)
- 선언했는데 실속 미만 → `INITIAL_MODE_UNSUPPORTED`로 거절.
  합성 헤드는 **방향만** 우리 것이고 크기는 미션 값이라는 근거

미션 8개에 `initial_speed_mps: 200.0` 명시. **이 값은 내가 정했다** —
계획 상한(2.0 u/s)이고 물리 대역 122~230 안이며, 원래 암묵적으로 받던
순항 인계를 명시한 것. **검토 포인트**: 도메인상 이 값이 맞는지.

부수 효과(좋은 쪽): r4 최소 AGL 10.2 → 29.1 m, 피크 102.2 → 98.5%.

### 2.6 `2d4bd7c` 자체 리뷰에서 나온 수정 3건

적대적 리뷰 워크플로에서 내 변경의 구멍 3개가 살아남았다:

1. **하한 미만 거절이 체인 모드에만 있었다.** FSM 단발 경로는 헤드를
   `if (start_vel_commanded_)`로만 검증해, `chain/enable:=false`면 선언한
   50 m/s가 `[STALL-FLOOR]`로 흘러가 132 m/s가 됐다. 규칙을
   `PathManager::statedStartSpeedProblem` 한 곳으로 옮기고 두 진입점이
   같이 읽게 함. 바닥값은 클램프와 같은 `stallFloorUnits()`
2. **지형 클리어(world=none)가 영수증 없이 맵을 지웠다.** 패널이 캐시한
   영수증이 이미 버려진 맵을 계속 보증. 클리어 시 해상도 0 센티널 발행
3. **`synthclamp` 뒤집기로 `[STALL-FLOOR]` 클램프가 무테스트가 됐다.**
   궤적 유래 헤드에는 클램프가 여전히 옳으므로 세 경우를 다 고정

### 2.7 상위 `b2773ed` RViz 미션 게이트 — 33초 대기

`[TERRAIN-READY]` 게이트가 **기다리는 영수증을 스스로 지웠다**
(`mission_config_panel.cpp` `ready_res_u_ = -1.0`).

terrain_publisher는 응답 **전에** 회랑을 발행하고(`terrain_publisher.py:187`),
ReplanFSM은 지형 메시지당 영수증을 **1회만** 낸다
(`replan_fsm.cpp:1137-1147`). 실측: 영수증이 서비스 응답보다 **88 ms
먼저** 나간다. rviz2는 같은 38.5 MB GridMap을 구독 패널마다 메인
스레드에서 역직렬화해 Qt 타이머를 몇 초씩 굶긴다.

증거(사용자 실제 세션 12개): 회랑 수신 → 미션 명령이 **33.0초**가 7개
(32.99~34.30), 게이트 이전 세션은 1.92초.

지우는 줄 제거. 매칭이 이제 **범위(extent)까지** 비교하므로 모서리+
해상도+범위가 같으면 같은 회랑이라는 근거. `MissionConfigPanel`의
죽은 `/terrain/grid_map` 구독도 제거(`terrain_resolution_`은 쓰기만 하고
읽는 곳 없음).

**검토 포인트**: "같은 미션 재실행 시 즉시 통과가 옳다"는 내 논증.

### 4.1 구역을 한 번도 싣지 않았다

ObstacleScenario 패널이 `/mission/risk_zones`로 따로 발행한다. 내
헤드리스 스모크는 그걸 보낸 적이 없다. 모든 로그가
`setRiskZones: 0 zones`.

그래서 다음이 **근거 없는 상태였다**:
- `docs/planning_perf_notes.md` §5.1의 9미션 표(r6·r7 포함)
- "r6·r7의 위반은 기존 특성" 판단

### 5.2 틀린 기계론을 코드에 커밋했다가 철회 (`7298af2` → `3f3a92c`)

`map_ceiling_headroom` 하향의 선행 조건으로 "천장이 구역 상단을 덮게"
고쳤다. `zonewall` 회귀가 깨졌고, 로그에서 측지선이 8.2 km까지 솟구쳐
포락선 94~99% 위반으로 전부 기각되는 걸 보고 **"상자를 키우면 못 나는
경로가 만들어진다. 이 누락은 안전장치다"**라고 결론내고 커밋했다.

틀렸다. 근거:

- 같은 로그 안에서 **천장 157.51 → 상승 47.33**, **천장 112.68 →
  상승 81.55**. 천장을 더 줬는데 덜 올라갔다
- 천장 111.18인 단계는 23.93까지만 올라가 **CLEAN 통과**. "모든 solve가
  죽는다"도 거짓(3단계 중 2단계)
- 구역을 실제로 싣고 천장을 4배 범위로 흔드니 측지선이 **미동도 안 함**
  (r6 21.47/35.47/53.82 → 전부 `[1.99, 6.60]`)
- **내 문서 §5.1이 이미 반증하고 있었다** — 천장을 1400 m 낮춰도 9미션
  궤적 동일. 상자가 유인이면 그럴 수 없다

기각 자체는 유지하되 이유를 바꿨다: **이득 없고 비용만**(r6 +44%).

`zonewall`은 `risk_vertical_ratio`를 생산값의 8.6배로 올려 넘어가기를
봉인한 픽스처라, 천장을 올리면 픽스처의 전제가 무너진다. 생산이 그렇다는
증거가 아니었다.

## 6. 아직 증명 못 한 것 / 열린 질문

### 6.1 `map_ceiling_headroom` 20 → 6 (보류)

찬성 근거: 구역 유무 무관하게 측지선 불변, 전단 25~35% 단축.

**막고 있는 것**: 구역을 실은 측정에서 측지선이 동일한데 최종 최소 AGL이

### 6.2 구역 있는 조건에서 어젯밤 변경이 안전한가 — **미확인**

수정 전 코드에 구역을 넣고 돌린 적이 없다. 그래서 r4·r3가 구역 있을 때
한계를 넘는 것(106.6% / 101.9%)이 기존 특성인지 내 변경 탓인지 **모른다.**
다음에 할 일로 잡아 뒀다.

### 6.3 전단과 뒷단의 등판각 불일치 (기록만)

실패한 단계들의 기각 사유가 고도가 아니라 **최대 추력·뱅크각**이었다.
전단 측지선은 모델의 **30° 유효 원뿔**까지 그릴 수 있는데, 추력으로
지속 가능한 등판각은 **~7°**다. 그 7°를 `segment_chain_planner.cpp`가
이미 계산하면서 전단에 안 넘긴다. 상자 문제가 아니라 이쪽이 실제 갭.

### 6.4 3단계 감사에서 나왔으나 손대지 않은 것 (사용자 결정)

- **말기 단계가 사실상 없다.** 유일한 생성기(헬릭스 하강)가 목표에서
  출발해 목표를 지나친다. `chain/terminal/enable`을 켜면 모든 미션이
  목표를 지나치는 나선을 받는다
- **판정기가 전이만 면제하고 말기는 순항 기준으로 심판한다.**
  "순항 도달" 래치가 비행 전체 단위라, 감속하는 말기가 생기면 멀쩡한
  계획도 강등된다
- `last_env_peak_` fail-open 센티널(5줄)

### 6.5 r3 시나리오 계열 미검증

r3는 시나리오가 6개인데 가장 빡센 `dense_corridor` 하나만 돌렸다.
