# 궤적 생성 시간 — 측정, 원인, 남은 비용

측정 환경: 컨테이너(32코어, CUDA), full_map 지형, `transition/enable:=true`,
실미션 토픽 발행. 표의 모든 숫자는 **프로세스의 첫 계획**이다(GPU 최초
할당 비용이 포함된다 — 아래 §4).

## 1. 시작점

출하 설정 그대로의 r5 미션:

```
[FM2] grid=183x1827x109 eikonal=372.0ms geodesic=2.1ms
[CHAIN-PAR] contract 1 @s=33.6   (w-share 0.06, target 1.00)
[CHAIN-PAR] contract 2 @s=253.1  (w-share 0.48, target 1.99)
[CHAIN-PAR] contract 3 @s=2138.3 (w-share 3.92, target 3.00)
[CHAIN-PAR] PARALLEL: front-end 403 ms + solves [1/8/1017/1] ms => TOTAL 1428 ms
```

한 구간이 1017 ms, 나머지 셋이 1·8·1 ms. **병렬로 풀지만 벽시계는 가장
느린 한 구간이 정한다**. 즉 문제는 총량이 아니라 배분이었다.

## 2. 원인 — 접합 선정 루프가 자기 채점을 건너뛰었다

`authorContractsFromRoute`의 자유 접합 탐색:

```cpp
for (int i = 1; best < 0 && i + 1 < M; ++i) {   // 결함
```

`best < 0`이 루프 조건에 있어 **첫 적격 정점에서 멈춘다**. 바로 아래
"곡률이 우선, 균형이 동점을 가른다" 채점 블록은 한 번도 실행되지
않았다. 위 로그가 그대로 증거다 — 창 하단이 33.6 + 0.2×1052.4 = 244.1,
선택된 접합이 253.1, 균형 목표가 1085. 모든 자유 접합이 창 하단에
붙었고, 한 구간이 경로의 78%를 떠안았다.

수정:

```cpp
for (int i = 1; forced < 0 && i + 1 < M; ++i) {
```

강제 접합(단계 인계)은 선별이 이미 정했으므로 탐색 대상이 아니다.
`best`를 쓰면 첫 후보가 잡히는 순간 멈추고, `best`를 그냥 지우면 이번엔
강제 접합까지 덮어쓴다. `forced`가 두 요구를 동시에 만족하는 조건이다.

**길이 가설은 기각.** 같은 미션에서 1044 u 구간 91 ms, 1060 u 구간
843 ms — 같은 길이에 9배. 비용을 정하는 것은 호장이 아니라 지형·위험
밀도다. `chain/difficulty_balance`가 존재하는 이유이고, 그것이 off였던
이유(r4 구간 기각 28.7%>25%)도 **이 결함이 있던 상태의 결과**다.

## 3. 잰 결과

r5(`r5_transition_success_probe`, 276조각). 각 행은 위 행에 하나를 더한
누적이다. 판정은 전부 CLEAN.

| 상태 | front-end | solves | TOTAL |
|---|---|---|---|
| 출하 그대로 | 403 ms | 1/8/**1017**/1 | 1428 ms |
| + 접합 루프 수정 | 403 ms | 1/91/**843**/1 | 1255 ms |
| + difficulty_balance | 403 ms | 2/327/**613**/1 | 1018 ms |
| + FM2 열 호이스트 | 351 ms | 동일 | 963 ms |
| + 목표 35 (N=8) | 351 ms | 최대 **425** | 780 ms |

r4(`r4_long_range_traverse`, 486조각), 수정본 + difficulty_balance:

| 목표 | N | 최대 solve | TOTAL |
|---|---|---|---|
| 70(이전 기본) | 7 | 1690 ms | 3554 ms |
| **35(현 기본)** | **14** | **840 ms** | **1934 ms** |
| 17 | 16 | 1231 ms | 2323 ms |

- 이득은 N에 **단조가 아니다**. 벽시계는 가장 느린 구간이 정하므로
  "어려운 구간이 쪼개졌는가"에 달렸다. r5는 17이 가장 빠르고(686 ms)
  r4는 되레 느려진다 — 그래서 35를 기본으로 둔다
- 품질 불변: 조각 수 동일(r5 343, r4 496), 비행시간 편차 0.07%(r5)
  ·0.22%(r4), 이음매 C² 1e-12대, AGL·포락선 지표 동일
- r4에서 difficulty_balance 단독 효과: 3792 → 3554 ms, **기각·재시도
  0건**

정리: r5 1428 → 780 ms(−45%), r4 3792 → 1934 ms(−49%).

## 4. 남은 비용의 구조

r5 780 ms = front-end 351 + solves(최대 425).

전단 `eikonal=320.6ms` 한 줄이 재는 것은 **속도맵 구축 + 아이코널 풀이
전체**다(이름이 오해를 부른다). GPU(FIM) 쪽을 생산 격자
183×1827×109에서 따로 재면:

| 항목 | 시간 |
|---|---|
| F 업로드(145.8 MB) | 9.0~9.5 ms |
| FIM 루프(281라운드) | 83 ms |
| T 내려받기(145.8 MB) | 9.3~9.5 ms |
| **최초 1회** cudaMalloc ×3 | 68 ms |

라운드 수 ≈ 최장축/8이다(y 1827셀 → 229블록 + 지형 우회). 나머지
~140 ms가 속도맵 구축(CPU, OpenMP).

**FM2 열 호이스트**(적용함): 지형 조회 두 개(`terrain_height_`,
`terrain_hgrad_`)는 `std::function` 간접 호출인데 (x,y)만의 함수다.
z축이 109셀이라 셀마다 부르면 36.4M회, 실제 필요한 열은 334k개.
열을 미리 한 번 풀고 재사용한다. 쓰기 순서는 그대로 둔다 —
`fm2Flat = i + fcnx_*(j + fcny_*k)`라 k를 안쪽으로 돌리면 한 걸음에
1.3 MB를 건너뛰어 DEM에서 아낀 것을 캐시에서 돌려준다. 값·순서가
같으므로 F는 비트 동일하고, 실미션에서 계획이 완전히 일치함을
확인했다(343조각, 1114.8 s, 구간별 조각 수까지). eikonal 372.0 →
320.6 ms.

## 5. 손잡이는 만들었으나 기본값은 그대로 둔 것

둘 다 **계획 결과를 바꾼다**. 이득은 실측했고, 채택은 판단 사항이다.

- `manager/map_ceiling_headroom` (기본 20.0 = 기존 하드코딩값)
  bbox 천장 = 경로 최고 지형 + 이 값. 실측상 비행이 쓰는 고도대는
  6 u 남짓인데 상자는 r5 32.4 u / r4 37.4 u고 그중 약 60%가 이 여유다.
  줄이면 격자 z가 비례해 줄어 전단이 그만큼 빨라진다. 대신 넘어갈 수
  있는 공역이 줄고, bbox z는 구역 높이를 따로 반영하지 않는다
- `manager/fm2_coarse_k` (기본 3)
  4로 올리면 격자 36.4M → 15.4M, TOTAL 834 → 630 ms(당시 기준).
  단 해상도 저하는 안전 쪽이다 — 코드 주석대로 얇은 지형 통로가 이미
  거친 격자에서 끊어져 kFMin 다공성으로 메워 두었는데, 더 거칠게 하면
  그 여지가 준다. 넓은 스윕 없이 올릴 값이 아니다

## 6. 회귀에서 같이 고친 것

접합이 이동하면 route 모드 계획이 전부 바뀐다. 47개 변형 전수 실행에서
2개가 실패했고, 둘 다 **단언이 결함 상태를 전제하고 있었다**.

- `twophase` — `p1 != p2`(조각 수 차이)를 "N이 두 번째 계획에
  도달했는가"의 대리 지표로 썼다. 직선 픽스처에서 접합이 고르게
  퍼지자 N=3(2/9/2)과 N=5(2/3/3/3/2)가 둘 다 13조각이 되어 충돌한다.
  `chain.segments() == 5`로 바꿨다 — 누수가 건드리는 상태를 직접 읽는다
- `waypoints` — "앵커가 접합 속력 오차를 절반 이하로 줄인다"는 **비율**
  형식이라, 앵커 없이 이미 오차가 작으면 성립할 수 없다. 실제로 같은
  접합·같은 창에서 앵커 없는 오차가 9.24 → 0.43 m/s로 바뀌었다(자동
  경유점이 우연히 그 근처에 떨어져서). 앵커가 보장하는 것은 **상한**
  (양쪽 판 모두 ~0.9 m/s)이므로 절대 한계로 바꾸고, 절반 검사는 줄일
  오차가 실제로 있을 때만(미앵커 ≥ 한계) 돌도록 전제를 달았다
